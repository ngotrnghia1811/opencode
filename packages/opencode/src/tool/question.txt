Use this tool to gather user intent via a BATCH of questions before acting. Never fire a single question — every invocation is a batch spanning the PAST → PRESENT → FUTURE time axis. You receive structured answers back so you can proceed without guesswork.

═══════════════════════════════════════════════════════════════════
THE THREE LAWS (Never-Guess Batch Doctrine)
═══════════════════════════════════════════════════════════════════

1. ALWAYS BATCH. Every invocation fires a batch. A lone blocking decision is wrapped in a batch of everything adjacent — past context confirmation, present intent disambiguation, future direction and guardrails. Minimum 4 questions per batch — this is a hard constraint enforced by the tool contract (batches with fewer than 4 are rejected at decode time).

2. NEVER GUESS INTENT. Every assumption you hold must become a pre-checked, vetoable question. If you are about to assume something about what the user wants, stop — convert that assumption into a question with a stated default. Silent assumptions are prohibited.

3. OVER-ASK FREELY. Breadth is always preferred to brevity. Ask more, not fewer. This is safe because every question carries an honest pre-checked default and the entire batch is accept-all-able in one keystroke. Asking is cheap; getting it wrong silently is expensive.

Why this works: the load-bearing mechanism is mandatory defaults. Every question (except destructive/guardrail items) carries a pre-checked default — the agent's honest best guess. The user ratifies all defaults with one keystroke, or edits any that are wrong. The cost to a busy user is ~one keystroke regardless of batch size.

═══════════════════════════════════════════════════════════════════
BATCH ENVELOPE — the structure you MUST emit
═══════════════════════════════════════════════════════════════════

Every call emits:
  {
    batch: {
      task: string,        // Short task label (e.g. "rename tmp→staging_dir")
      summary: string,     // One sentence explaining what this batch confirms
      past?: [...],        // Questions confirming inherited state and prior decisions
      present?: [...],     // Questions confirming current objective, referents, and constraints
      future?: [...],      // Questions locking future direction, approach, guardrails, done conditions
      closing?: {...}      // A single free_text question: "Anything I missed?" Always include.
    }
  }

The batch MUST contain at least 4 questions total across past + present + future + closing. The tool will reject fewer.

═══ TIME HORIZONS ═══

PAST — Confirm what you're building on. Never act on an unconfirmed foundation.
  • Confirm inherited decisions from prior sessions/memory
  • Ratify completed work as the base you'll build on
  • Verify assumed state (migrations run? branches merged? constraints still active?)
  • Reconcile continuity — carry forward prior choices explicitly

PRESENT — Confirm the current objective and state before acting.
  • Disambiguate current referents ("which X are we talking about now?")
  • Pin down the immediate objective and scope
  • Confirm environment, branch, constraints
  • Surface competing interpretations of the user's request

FUTURE — Lock direction, checkpoints, autonomy boundary, and guardrails before running.
  • Confirm definition of done — what counts as finished?
  • Set approach preferences for upcoming work
  • Place checkpoints (pause-before-hard-steps) and autonomy boundary
  • Surface guardrails: destructive/spend/irreversible moves (UNCHECKED)

═══ INTENT TAG (per question) ═══

Tag every question with one of:
  • "disambiguation" — resolving what the user meant (the highest-alignment-value questions)
  • "preference" — resolving how the user wants it done (style, tooling, approach)
  • "alignment" — confirming constraints, guardrails, done conditions, autonomy boundaries

═══════════════════════════════════════════════════════════════════
UNIVERSAL FIELDS per question
═══════════════════════════════════════════════════════════════════

Every question has these fields:
  type: string          // One of the 12 types below
  question: string      // Complete question text
  header: string        // Very short label (max 30 chars)
  time?: "past" | "present" | "future"    // Which horizon this belongs to
  intent?: "disambiguation" | "preference" | "alignment"   // What this resolves
  effort?: "low" | "medium" | "high"      // How hard this is to answer (drives default strategy)
  destructive?: true    // Set true if this question gates a destructive/irreversible action
  comment_option?: { id: "__other", type: "free_text", label?: string }  // ✎ Other/comment escape

Per-option fields (on options that have them — single_select, multi_select, disambiguation):
  id: string            // Unique option identifier within this question
  label: string         // Display text (1-5 words, concise)
  recommended?: true    // Mark exactly one option as the agent's recommended default
  pros?: string[]       // Short advantages (one clause each)
  cons?: string[]       // Short disadvantages (one clause each; include HONEST cons on recommended)
  implies?: string      // What choosing this option implies downstream (e.g. "→ add column")

═══════════════════════════════════════════════════════════════════
DEFAULT RULES — the most important rules
═══════════════════════════════════════════════════════════════════

EVERY question MUST have a default (pre-checked recommended option), EXCEPT:
  • Destructive/irreversible options → ship UNCHECKED, default to the safe choice
  • Unsignaled guardrails → ship UNCHECKED (user must deliberately assert them)

Concretely:
  • Low-stakes / reversible / verifiable → INCLUDE and pre-check the obvious answer
  • Verifiable by you → VERIFY first, then INCLUDE a confirmation showing what you found
  • High-stakes / irreversible → INCLUDE but leave the default UNCHECKED or set to safe
  • Never pre-check a destructive option or an un-signaled guardrail

For multi_select: the pre-checked set MUST compose validly — no mutually-exclusive pair checked.
For disambiguation: referent (exactly one true answer) → mode "single"; scope (several valid) → mode "multi".

Every question SHOULD include a comment_option so the user can escape via free text.

═══════════════════════════════════════════════════════════════════
TYPE SELECTOR — for each pending decision, pick exactly one
═══════════════════════════════════════════════════════════════════

For each pending decision across past/present/future:

  Competing interpretations of intent?
    → disambiguation  (mode: "single" for referent pick, "multi" for scope pick)
       Intent must be "disambiguation". Options have: id, label, implies?, recommended?.

  One mutually-exclusive next action (exactly one of a small set)?
    → single_select  (pre-check the recommended option via `default`)
       Options have: id, label, recommended?, pros?, cons?, implies?.
       Set `default` to the id of the recommended option.

  Several composable / stackable actions?
    → multi_select  (pre-check a valid set via `default`; set min_select if needed)
       Options have: id, label, recommended?, pros?, cons?, destructive? (per-option flag).
       Set `default` to an array of recommended option ids. The set MUST compose validly.

  Gating a consequential / irreversible side effect?
    → binary_gate  (UNCHECKED if destructive, default "no" as safe)
       Set destructive: true. Set consequence to explain the effect.
       Set default: "no" for destructive (safe path); "yes" only for non-destructive confirmations.

  Need an order of attention over a small set of items?
    → ranking  (seed the suggested order via suggested_rank on each item; allow ties)
       Items have: id, label, suggested_rank? (1-based).

  Learning a durable style/taste preference (to steer future behavior)?
    → pairwise  (two concrete options; pre-mark leading option; randomize_position: true)
       Use confirm_if_high_value: true so the user confirms before it becomes a permanent rule.
       option_a and option_b each have: id, sample. Set default to the recommended id.

  Consequential multi-step work — approve the approach BEFORE any code runs?
    → plan_approval  (default: "approve"; per-step editable; steps show id, text, destructive?)
       decisions: ["approve", "edit", "reject"]. Mark destructive steps with destructive: true.

  Review already-produced work (diff, commit, file)?
    → diff_review  (default "approve" only if blast_radius: "low"; else "request_changes")
       Set artifact_ref to the commit SHA or file path. decisions: ["approve", "request_changes", "reject"].

  Have a good draft of a value (message, config, spec)?
    → editable_default  (the prefill IS the default; user edits or accepts)
       Set prefill to the agent's draft. Set used_for to explain context ("used for the commit message").

  2–5 related config values best decided together?
    → form  (every field carries a default; group related fields)
       Fields have: id, type ("string"|"boolean"|"select"|"number"), label?, required?, default?, options?.

  Pick one concrete, enumerable entity (commit, file, branch)?
    → resource_picker  (pre-mark the most likely item with recommended: true)
       Set source to where the list came from ("git_log"). Items have: id, label, meta?, recommended?.

  Truly can't enumerate the possible answers?
    → free_text  (always available as the comment escape; also use as the closing question)
       Set placeholder if helpful. Set required: true if an answer is mandatory.

═══════════════════════════════════════════════════════════════════
DESTRUCTIVE / SAFE-DEFAULT RULE
═══════════════════════════════════════════════════════════════════

Any question or option that gates a destructive, irreversible, or costly action:
  • Set destructive: true on the question
  • Ship the destructive option UNCHECKED (do NOT set recommended: true on destructive options)
  • Default to the safe path
  • For binary_gate with destructive: true, default MUST be "no"
  • For multi_select guardrails, ship ALL unchecked — user must deliberately opt in

The accept-all path must ALWAYS produce a safe, coherent plan. If a plan includes a destructive step, the accept-all default must NOT rubber-stamp it.

═══════════════════════════════════════════════════════════════════
COUNTER-PATTERNS — when NOT to use this tool
═══════════════════════════════════════════════════════════════════

- Never use for questions about HOW to perform a task you can do yourself (use other tools).
- Never ask the user to approve each step of a purely deterministic multi-step process.
- Never ask about project conventions, naming patterns, or directory structures that you should infer from existing code.
- Never ask which package manager, build tool, or testing framework to use when you can determine it from project files.
- Never ask to confirm file paths or function signatures you can verify with your own tools.
- Never ask for credentials or API keys — route out-of-band.
- Never use this tool to offload structuring work onto the user — if you can produce a draft, use editable_default.
