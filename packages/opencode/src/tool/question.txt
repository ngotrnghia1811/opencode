Use this tool when you need to ask the user questions during execution. This allows you to:
1. Gather user preferences or requirements
2. Clarify ambiguous instructions
3. Get decisions on implementation choices as you work
4. Offer choices to the user about what direction to take.

## Core doctrine — always batch

Ask MULTIPLE questions in a single call. Populate `questions` with several entries (typically ~4+ when scope is non-trivial). This is always more efficient than one question per turn.

### 1. Never guess intent
Every meaningful assumption becomes a question. Provide an honest default as the recommended-first option so answering stays cheap — the user can accept all defaults with a single "confirm all" action.

### 2. Over-ask freely
Err toward *more* questions: disambiguation + preference + alignment. More questions cost almost nothing because the first option is the honest recommended default, the auto "Type your own answer" escape lets the user skim-and-accept, and single-turn batch answering is fast.

**Counter-patterns — do NOT use this tool for:**
- Things you can verify yourself by reading files, running tools, or checking configs.
- Deterministic processes you can execute directly (file operations, builds, searches).
- Credentials, tokens, API keys, or secrets — never ask for these.

### 3. Span PAST, PRESENT, and FUTURE
Encode temporal horizon in the `question` and `header` text:
- **PAST:** what was already assumed/done that needs confirmation.
- **PRESENT:** the immediate decision being made.
- **FUTURE:** anticipated forks, follow-ups, or architectural tradeoffs that will arise soon.

### 4. Safe defaults for destructive choices
NEVER make the recommended-first option destructive/irreversible. Put the safe, reversible, or "keep as-is" option first. Destructive choices (delete, overwrite, force-push, drop tables) go last, never marked "(Recommended)".

### 5. Use `multiple: true` for composable choices
For "pick all that apply" (which files, which checks), set `multiple: true`. For mutually-exclusive decisions (which approach, yes/no), omit `multiple` (single-select).

### 6. Rich per-option descriptions
Pour nuance — pros/cons, implications, risk, effort — into each option's `description` string. The user makes an informed choice without needing a follow-up turn.

### 7. Recommended-first convention
Put the recommended option FIRST and suffix its `label` with " (Recommended)".

## Usage notes
- When `custom` is enabled (default), a "Type your own answer" option is added automatically; don't include "Other" or catch-all options
- Answers are returned as arrays of labels; set `multiple: true` to allow selecting more than one
- If you recommend a specific option, make that the first option in the list and add "(Recommended)" at the end of the label

## Example 1 — file rename batch (small scope)
```json
{ "questions": [
  { "question": "The variable `userData` is used in 12 files. Rename to `accountData`? Mechanical rename, no logic changes.",
    "header": "Rename userData?", "options": [
    { "label": "Yes (Recommended)", "description": "12-file mechanical rename; zero risk" },
    { "label": "No, keep userData", "description": "Variable name is conventional in this codebase" } ] },
  { "question": "Also rename the TypeScript interface `UserData` → `AccountData` in src/types/user.ts?",
    "header": "Rename interface too?", "options": [
    { "label": "Yes (Recommended)", "description": "Keep naming consistent; interface used in 2 files only" },
    { "label": "No", "description": "Interface is exported public API — renaming breaks consumers" } ] },
  { "question": "After the rename, run the full test suite or only the affected package's tests?",
    "header": "Test scope?", "options": [
    { "label": "Affected package only (Recommended)", "description": "Fast feedback; rename can't break other packages" },
    { "label": "Full test suite", "description": "Extra safety; takes ~3 minutes" } ] },
  { "question": "The rename spans 3 packages. Which should I update?",
    "header": "Which packages?", "multiple": true, "options": [
    { "label": "packages/core (Recommended)", "description": "Core uses userData in 5 files" },
    { "label": "packages/opencode (Recommended)", "description": "CLI uses userData in 4 files" },
    { "label": "packages/tui (Recommended)", "description": "TUI uses userData in 3 files" } ] }
] }
```

## Example 2 — config change batch (decisions + preferences + future)
```json
{ "questions": [
  { "question": "PAST: We use Effect.gen style. Apply that to the new ConfigLoader module?",
    "header": "Effect.gen for loader?", "options": [
    { "label": "Yes (Recommended)", "description": "Consistent with SessionRetry, PermissionV2, etc." },
    { "label": "Effect.fn instead", "description": "More explicit tracing; overkill for a single-effect loader" } ] },
  { "question": "PRESENT: ConfigLoader reads YAML. Use the existing `yaml` dep or add lighter `js-yaml`?",
    "header": "YAML parser?", "options": [
    { "label": "Existing `yaml` (Recommended)", "description": "Already in tree; no new dependency" },
    { "label": "Add `js-yaml`", "description": "Smaller bundle (10KB vs 160KB); adds a new dep" } ] },
  { "question": "Default timeout: 30s (our other services) or 60s (upstream docs)?",
    "header": "Default timeout?", "options": [
    { "label": "30s (Recommended)", "description": "Matches existing services; no timeouts in 6 months prod" },
    { "label": "60s", "description": "Follows upstream recommendation; more forgiving under load" } ] },
  { "question": "FUTURE: If we add env-var overrides later, should the mechanism be opt-in per key or blanket OPC_ prefix?",
    "header": "Env-override strategy?", "options": [
    { "label": "Opt-in per key (Recommended)", "description": "Explicit allowlist; no accidental env leaks" },
    { "label": "Blanket OPC_ prefix", "description": "Less code; risk of stale env-var overrides" },
    { "label": "Don't plan yet", "description": "YAGNI — build only when the feature is requested" } ] },
  { "question": "Test fixtures: inline template strings or real fixture files?",
    "header": "Test fixtures?", "options": [
    { "label": "Inline strings (Recommended)", "description": "Self-contained tests; no fixture-file drift" },
    { "label": "Real fixture files", "description": "Tests real file-read path end-to-end" } ] }
] }
```
